## Outcome vs. plan

the same way M1-11 was split into a/b) landed on `milestone/M2`. No task was dropped. One real

session discovered that no earlier card had actually assembled M2-08 through M2-14's standalone,

## What the gate caught / what it missed

**Gate catches, working as intended:** `M2-06`'s comms/accusation/confrontation/vote policy suite
correctly enforces INV-5/10/13 (policies read only the actor's scoped view) from the start, and
`M2-15b`'s sim wiring found the real INV-5/10 zero-unique-attribution property holding across
L2/L3/L5 — no ambiguity regression was introduced by wiring real mechanics past M1's bot-decision
layer.

**The single largest gate miss of this milestone, by a wide margin:**

1. **`milestone/M2`'s CI `gate` job (`pnpm test`) has been failing on every push since
   2026-07-19T20:18** (`feat(m2): add black-box artifact assembly and verification` was the last
   green run) — the entire second half of the M2-15b session, and both of this retro-session's own
   merge/deferral pushes. `gh run list --branch milestone/M2` shows this directly. **Nobody caught
   it because M2 never opened a PR** (by design — the grandfathered single-PR-at-milestone-end
   model), so there was no required-check surface forcing anyone to actually look at push-triggered
   CI on the milestone branch for a full week. This is exactly the shape of gate-miss both prior
   retros named as the common thread ("the gate can't observe its own blind spot") — except this
   time the blind spot is procedural, not technical: a real, currently-red check that nobody was
   watching, on a branch model that structurally defers all review to milestone end.

   Root cause: `packages/ui-shared/src/SocialApp.test.tsx` and
   `packages/ui-shared/src/shared-screen/social-scene.e2e.test.tsx` (both declare
   `// @vitest-environment jsdom`) call the real `encryptMessage`/`importKey` from
   `packages/transport` to simulate an inbound phone message, and jsdom's own `crypto.subtle` shim
   rejects a real Node-realm `ArrayBuffer` passed into it — evidently only under whatever jsdom+Node
   combination GitHub Actions' now-forced Node 24 runner produces (the workflow requests Node 20;
   `actions/setup-node@v4` is silently substituting Node 24 per its own deprecation notice). This
   does **not** reproduce locally (Node v26) and does **not** implicate the crypto logic itself —
   `packages/transport/src/protocol.test.ts`'s plain-`node`-environment unit/property tests for the
   same `encryptMessage`/`importKey` pass everywhere, before and after this appeared. It also isn't
   a shipped-product defect: a real browser tab is one JS realm, so this specific failure mode has
   no path to an actual player's session. But it is a real, currently-open defect in the gate's
   ability to prove the assembled app's crypto path works end-to-end — filed as `docs/tasks/BL-09.md`,
   and unlike `BL-02`/`BL-07`/`BL-08` below, **this one genuinely blocks the milestone PR** per Plan
   §6.1's automated-gate requirement, not something the owner can simply defer.

## Spec health

Two amendments landed *during* M2 rather than being deferred to this retro, keeping Appendix A and
§21.2's invariant-mapping current per Plan §7's every-PR discipline: the commit-reveal section (§6)
was rewritten to describe the two-stage seed-commitment-then-draw-commitment scheme `M2-01`/`M2-02`
actually built, and the agenda section (§10.2) plus Appendix A's worked trace were updated for the
2026-07-18 forced-vote redesign (`envelope.opened` only follows a carried majority `vote.recorded`,
never voluntary). Both are real, already-committed Spec edits, not open questions.

**Extrapolation notes from the M2-15b session, proposed for this retro's triage** (each is a
genuine, correct guess the Spec doesn't prescribe — surfacing them here closes the "unrecorded
correct guess is a defect" gap, but the disposition on each is this session's recommendation, not
a decision; per Plan §7 that's the owner's call, same as the M1 retro's Spec-health section left
its own proposal open rather than landing it unilaterally):

1. **Envelope contents for a forced burn are extrapolated, not Spec-derived.**
   `resolveConfrontation`'s `contents` field is opaque; `host-session.ts`'s `envelopeContentsFor`
   maps the deck's routine objective to `"LOYAL"` and any real agenda to that agenda's own id as
   the marker. **Proposed: log as a Spec §24 open question** — a real renderer will still need to
   turn either into MAGGIE-voiced prose, and the Spec should eventually say what the marker means,
   not just that implementers invented one that works.
2. **Reconnect-by-resent-claim-token.** `receiveClaim` treats a claim token arriving under a new
   peer id as reconnect rather than `claimed-by-other` — extrapolated from §7's "retry while offer
   is valid" plus token possession being the only credential that ever existed. **Proposed: sound,
   no Spec silence remains** — reads as a correct application of an already-stated rule, not a gap;
   no amendment needed, but the owner should confirm rather than take this session's word for it.
3. **`vote.cast`'s voting context (eligible players, target's objective fact, envelope contents) is
   host-derived from ledger state, never client-supplied** — reasoned from INV-13 (a client payload
   must never carry referee-adjacent state), not stated anywhere as "the host derives it here
   specifically." **Proposed: sound and load-bearing enough to promote from a handoff footnote into
   Spec §16 directly**, the same way the M1 retro promoted the `phases/commits.ts` lesson into
   CLAUDE.md. Not landed in this retro; the owner's call whether to land it now or defer.
4. **The `social-demo-4` campaign seed was hand-searched, not arbitrary.** The exit demo needs both
   "agendas dealt at the deck's own published odds" (0.28) and "two colliding actions" in the same
   run; most seeds at 0.28 across three seats don't reliably deal two agenda-holders. This seed was
   verified to deal the real agenda to two of three seats. **Proposed: content decision, not a Spec
   question** — recorded here so a future session doesn't rediscover this by trial and error before
   a demo.
5. **`advanceStep`'s "cross any leading automatic steps, then perform exactly one real step"
   semantics** are this session's own reading of what "one call" should mean once a phase script
   can start with an automatic step — not stated anywhere. **Proposed: log as a Spec §24 open
   question** for the phase-engine's `PhaseStep` semantics, parallel to M0's `DifficultyRef`/tick
   entries.

**None of the five dispositions above are landed in this retro** — unlike M0's retro, which had the
owner live in the room to decide each item on the spot, this retro was drafted without the owner
present to triage them. They're proposals awaiting the owner's actual review.
