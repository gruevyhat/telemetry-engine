## Outcome vs. plan

All fourteen M3 task cards (`M3-00` through `M3-13` — `M3-13` added mid-milestone, see below)
landed on `main`. No task was dropped, and — unlike M1 and M2 — nothing here was grandfathered
onto a milestone branch: M3 is the first milestone to run entirely under the two-tier method with
always-shippable trunk (per-task commit scopes, no PRs, red/green pairs straight to `main`).

**One task was added mid-milestone, following the exact pattern M1 and M2 both hit before it.**
`M3-11` was correctly split out at planning time as the plugin-assembly surface (its own Context
section names this explicitly: "This card exists because M1 and M2 both learned the same lesson
the hard way" — M1-13 and M2-15 each found late that no card had assembled standalone pieces into
a runnable whole). That worked exactly as intended *for the plugin object itself*. What planning
did not anticipate is that assembling a `Plugin` object and wiring it into the actually-shipped
browser app are two separate assembly surfaces — `M3-12`'s exit demo found that `App.tsx` never
registered `travellerPlugin` or called `resolveInformationHorizon` at all, the same "pieces built
in isolation, never reaching the running app" failure mode a third time. `M3-13` was opened to
close it, with the owner's explicit authorization, and closed the same session. **Proposed Plan §5
refinement below** (Actions): the "split out assembly at planning time" rule should name *both*
"a new package's internal composition" and "wiring that composition into the shipped app/UI" as
distinct assembly surfaces, since M3 shows a milestone can get the first right and still miss the
second.

**The other real, recurring signal this milestone: task cards under-specified `owned_paths` five
separate times**, all caught and fixed at implementation time rather than shipped wrong:

| Card | What was missing | Why |
|---|---|---|
| `M3-08` | `phases/commits.ts`, `ledger/kinds-v0.ts` | INV-6 means the actual ledger-append call and the fact-kind registration can't live in the card's own `economy/` files |
| `M3-09` | `phases/commits.ts`, `ledger/kinds-v0.ts` | same INV-6 shape, plus `edge.used` was catalogued in Markdown but never registered in code |
| `M3-10` | `plugin-traveller/src/index.ts`, its `package.json` dependency | the package had no public entry point at all before this card needed one |
| `M3-11` | `plugin-api/plugin.ts`, `plugin-api/index.ts`, `plugin-traveller/package.json` | the engine-side `Plugin`/`PersonaDef`/`Lexicon`/`DiceConvention`/`CheckResult` types didn't exist anywhere yet |
| `M3-13` | `economy/index.ts` | `resolveInformationHorizon` wasn't re-exported from the engine's public package surface either |

Every one of these is the same underlying shape: a card assumed a public interface or registration
step already existed, and it didn't, because the card that would have added it was scoped
narrowly enough to skip it. None caused a wrong shipped result — each was caught by the lead before
or during implementation, amended, and logged — but five-for-fourteen is a real decomposition-
quality signal, not noise (see Actions).

## What the gate caught / what it missed

**Caught, working as intended:**
- `check:packets` (new this milestone, `scripts/check-packet-commits.mjs`) mechanically enforces
  conventional-commit scoping, acceptance-test immutability, and worker-forbidden paths. Found its
  own bug once: it initially made a lead-authored acceptance test immutable *forever*, not just to
  the worker, which would have blocked the sanctioned "amend and re-dispatch" escalation outcome
  CLAUDE.md itself names. Fixed the same session (`fix(hooks)`) with a test proving the fix.
- `scripts/build-stub.mjs`'s INV-1 guard caught a real near-miss twice this milestone: a comment
  naming the Traveller package as a raw string (M3-03's original finding, PROJECT.md 2026-07-25;
  recurred verbatim as a fresh mistake in this session's own `commitEdgeUsed` doc comment, fixed
  immediately by rewording, not loosening the guard).
- The M3-10 worker (Haiku) correctly escalated two real bugs in the *lead's own* acceptance test
  (a jsdom/`import.meta.url` resolution issue, a character fixture shape mismatch) rather than
  silently working around them or guessing — exactly the escalation discipline the method asks for.

**Missed, or caught only very late:**
1. **`resolveEdge` (M3-09) resolved careers case-sensitively against capitalized registry keys**
   (`"Merchant"`), but real travtools exports are lowercase (`"merchant"`, confirmed by the
   already-committed `fictional-merchant.json`/`fictional-scout.json` fixtures). M3-09's own
   acceptance tests never used a real fixture, only hand-built inline objects — the bug shipped
   silently until M3-12 exercised the real fixture for the first time. Fixed same session.
2. **`EdgeProposal.t.slot` (M3-09) was typed `string`, not the engine's `BeatSlot` union** — so
   `useEdge`'s own output never actually typechecked into `commitEdgeUsed`, unproven because
   neither had a real caller until M3-11 wired them together. `pnpm typecheck` couldn't catch this
   because nothing called both functions in the same file until M3-11 existed.
3. **The headline miss:** `resolveInformationHorizon` (M3-05) had zero production callers from
   the milestone that built it until `M3-13`, four cards later. Every gate command
   (`test`/`typecheck`/`lint`/`build:stub`) passed the entire time, because a correct, tested,
   *unused* function is invisible to all of them. Only the exit-demo card's explicit mandate to
   prove Spec §21.3 "with historical remote pricing" — i.e., an acceptance criterion that names an
   observable outcome, not a function call — forced someone to go looking for a caller and find
   there wasn't one.

**Pattern across all three:** unit tests built from hand-constructed fixtures pass even when the
real, already-committed fixture would fail; and a function can be perfectly correct and totally
unreachable, and no gate command distinguishes that from "working." Both are why this milestone's
BL-10/BL-11 lesson ("run the actual thing") kept paying rent all the way to the end.

## Spec health

**Extrapolations from this milestone, proposed for triage** (each a genuine correct guess the Spec
doesn't prescribe, same discipline as M1/M2's retros — dispositions are recommendations, not
decisions; that's the owner's call):

1. **`JumpValidation`, `Ship`, `CrewMember`'s nullable `career`/`sourceHash`, `EdgeDef`'s
   `available`/`deferred` shape (all M3-03)** — already logged in PROJECT.md 2026-07-26. **Proposed:
   sound, no Spec silence remains worth flagging beyond what's already recorded.**
2. **The "structural typing over a workspace dependency" pattern, used four times (M3-01, M3-06,
   M3-07, M3-09) then explicitly reconsidered once (M3-11).** Not a Spec question, but a real,
   recurring architecture judgment call with no durable home — CLAUDE.md and the two-tier-method
   skill are both silent on when a plugin package should or shouldn't take an engine dependency.
   **Proposed: write down the actual rule** — a module avoids the dependency when it only needs a
   couple of small, stable shapes it can duplicate structurally (M3-01's `Distance`, M3-09's
   `BeatSlot`); a module takes the dependency when its entire job is conforming to an engine-owned
   interface (M3-11's `Plugin`) or when a sibling package already sets the precedent for the same
   reason (`plugin-stub`). Worth a short paragraph in the two-tier-method skill, not a new rule in
   CLAUDE.md — this is packet-decomposition judgment, not an every-turn constraint.
3. **`Plugin.economy.costs: CostModel` (Spec §15) is entirely unimplemented — `CostModel` has zero
   substrate anywhere.** M3-11 omitted it rather than invent one (PROJECT.md 2026-07-26). **Proposed:
   log as a Spec §15 open question**, the same treatment M2's retro gave `JumpValidation` before
   M3-03 defined it — a future milestone should either define `CostModel` for real or remove it
   from the interface, not leave it silently absent from every implementation.
4. **`Plugin.persona`/`Plugin.dice` (`PersonaDef`, `Lexicon`, `DiceConvention`, `CheckResult`,
   `DiceCheckInput`) didn't exist anywhere before M3-11 — Spec §15 names the shapes in pseudocode
   only.** The critical-success/failure convention (natural 2 auto-fails, natural 12 auto-succeeds,
   independent of modified total) is this session's own extrapolation from "the standard 2d6
   convention," not stated in the Spec. **Proposed: log as a Spec §6 open question** — a future
   plugin (or a rules-accuracy pass on this one) needs the Spec to actually say this, not just the
   Traveller plugin's own code comment.
5. **No session-lifecycle substrate anywhere (M3-09)** — "once per session" ships as "once per
   campaign" until a future milestone builds real sessions. Already logged and correctly deferred
   with no milestone attached (unlike Scout/Agent/Army's M4/M5), per PROJECT.md 2026-07-26.
   **Proposed: sound, already fully disposed of.**
6. **"Home"/"remote" hex for M3-13's distance check is the imported sector's own first two
   worlds** — this demo app has no ship-position/navigation model, so there's no independently
   tracked "current hex" to check a foreign sector against. **Proposed: content/demo decision, not
   a Spec question** — recorded so a future session doesn't rediscover the same constraint.

## Process health (two-tier method telemetry)

M3 is the method's first full milestone (M0–M2 predate it or ran under the old model). Signal,
not final judgment — one milestone is a small sample:

- **Escalations this milestone, by resolution:**
  - *Amend and re-dispatch:* M3-06/M3-07 (worker packets crossed `plugin-traveller`'s `rootDir`
    because the "no engine dependency" decision wasn't yet made when they were authored — resolved,
    re-dispatched, second attempt succeeded); M3-10 (worker correctly escalated two lead-side test
    bugs plus found one real bug of its own across two dispatch rounds).
  - *Reclassify as frontier work:* M3-09 (assumed a reroll operation, a session boundary, a
    `runtime edge.used` kind, and a phase-commit seam that didn't exist — all four were genuine
    public-interface/fact-kind decisions, correctly outside worker scope).
  - *Owner escalation (a third shape this milestone's format doesn't formally name):* M3-12 found
    that Plan §5's exit-demo language couldn't be honestly claimed and put the decision to the
    owner rather than deciding unilaterally or quietly lowering the bar. Worth naming as a distinct
    category in the method's documentation — "amend" and "reclassify" both describe a lead
    resolving a *worker's* escalation; this was the lead escalating *to the owner*, a different
    relationship the two-tier method's escalation format doesn't currently have a slot for.
- **First-pass worker success:** M3-01 (Haiku, first attempt, no escalation — cross-checked against
  travellermap's own reference implementation over 197,120 hex pairs, not just the lead's tests).
  M3-02's dispatch history isn't independently visible to this session beyond its commit pair.
- **Worker-to-frontier reclassification rate:** 1 of the milestone's worker-routed packets (M3-09)
  reclassified entirely before implementation began — the routing rule's own stated trigger (fact
  kinds, phase-engine interpreter) fired correctly.
- **No test was deleted, skipped, or weakened anywhere in M3.** Two acceptance tests were amended
  after their initial commit (M3-09's `edges.test.ts`, twice — once for a `BeatSlot` type fix, once
  for the case-insensitivity regression), both via the newly-fixed `check:packets` amendment path,
  both adding coverage, neither removing or loosening an assertion.
- **Concurrent-session hazard, worth recording:** a separate session (`BL-11` work) committed to
  `main` interleaved with this session's own commits throughout M3-08 through M3-13, confirmed by
  `git log` showing `test(bl-11)`/`fix(bl-11)` commits landing between this session's own commits,
  and by uncommitted BL-11 files regularly present in `git status` output that this session had to
  work carefully around (always `git add` by exact path, never `-A`, and re-check `git status`
  immediately before every commit — one commit was caught mid-session bundling five unrelated
  already-staged files from a prior step and had to be `git reset` and re-split). Always-shippable
  trunk with no per-milestone branch means this is now normal, expected operation, not an incident —
  but it's a new failure mode the old grandfathered-branch model never had to handle, worth a
  standing note for future sessions: **never assume the index only contains what you just staged.**

## Fun check

**Not applicable in M1/M2's sense, and that's a real gap worth naming rather than skipping past.**
M1 and M2's fun checks asked "is the trade loop / social scene actually fun to play." M3 has no
new player-facing gameplay loop of its own — it's import plumbing and one career-edge mechanic.
The closest analog is whether the newly-wired remote-market-check panel (`M3-13`) is a good
*experience*, not just a correct one: this session hand-verified it works (real distance, real
historical pricing, no console errors) but did not evaluate it for feel, clarity, or whether a
person unfamiliar with the code would understand what "Crew-supplied distance in parsecs" is for
without reading this retro. That's a real unknown, not a dismissed one — flagged for the owner's
own look, same spirit as M1/M2's fun checks, just scoped to what M3 actually shipped.

## Actions

**Triaged by the owner 2026-07-26, same session.** Against this project's own stated bar for
process additions — "add each only when its absence causes a concrete, recurring failure," not
"would this be nice to have written down" — three of the seven proposals below were rejected as
premature process addition (single-occurrence judgment calls, not recurring failures) rather than
landed reflexively. This is itself a small process-health data point: a retro's proposals are not
automatically actions.

1. **Plan §5 refinement: split "package-internal assembly" and "app/UI wiring" as two distinct
   assembly surfaces when a milestone introduces a new plugin or subsystem.**
   **Disposition: approved and landed in this commit.** Third occurrence of the identical failure
   (M1-13, M2-15, M3-12/13) clears the recurring-failure bar; the fix is one paragraph appended to
   the existing Plan §5 rule, not new process. See `docs/telemetry-engine-dev-plan.md` §5.
2. **Write down the "structural typing vs. engine dependency" decision rule** in the two-tier-method
   skill.
   **Disposition: rejected.** Never caused a defect, and M3-11 correctly *reversed* the earlier
   pattern within the same milestone — there is no stable rule to write down yet, only a judgment
   call made differently each time based on context. Documenting one now risks ossifying something
   false. The PROJECT.md decision log already carries the reasoning for whoever needs it next.
3. **Triage the four proposed Spec updates** (`CostModel`'s non-existence, `PersonaDef`/`Lexicon`/
   `DiceConvention`/`CheckResult`/critical-roll convention needing to move from code-only into the
   Spec itself).
   **Disposition: approved and landed in this commit.** Both logged as Spec §24 open questions
   (items 6 and 7), the same treatment as the M0 retro's `DifficultyRef`/`clock.tick` entries —
   no normative Spec text changed, so no version bump.
4. **Name the "owner escalation" category explicitly in the two-tier method's escalation format.**
   **Disposition: rejected.** Happened once. Handled fine without a documented category. Naming a
   taxonomy after a single instance is the premature-process trap the method's own "deliberately
   omitted until needed" section warns against — revisit if it recurs in M4.
5. **Decide whether five owned_paths amendments in one milestone warrants a packet-authoring
   checklist change** (e.g. a grep-before-`ready` step).
   **Disposition: rejected.** This adds a cost to every future packet forever to guard against
   something that's plausibly self-resolving: M3 was the first milestone building the plugin's
   public surface at all. Wait for M4/M5 evidence before paying that cost.
6. **M3-13's UX quality (Fun check) is unassessed — the owner should look at the shipped panel
   themselves.**
   **Disposition: addressed.** Owner watched a live hand-driven demo of the panel this session
   (real sector/character import, real distance, real historical pricing, in an actual browser
   tab). No formal feel/clarity assessment beyond that, by choice.
7. **`pnpm dev:shared`'s remote-market-check panel has no polish pass** (plain labels, minimal
   MAGGIE-voice copy, unrounded `Cr101.129`-style prices).
   **Disposition: stays deferred, no card opened.** Cosmetic, not a correctness issue, and M3 is
   otherwise fully closed — open a card only when this panel is actually about to face a real
   table.
