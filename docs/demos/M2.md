# M2 demo — the social scene: agenda deal, comms window, confrontation, black box

## What this proves

This local walkthrough proves Spec §21.3's M2 acceptance line and the Plan's M2 exit demo: pairing at least two phones to a local shared screen, dealing independent agendas at the deck's own published odds, completing a timed comms window with two colliding actions, surfacing an incident, carrying or failing an accusation vote, and verifying the campaign's black-box preimages at the end. Every step drives the real interpreter through real encrypted transport messages — no direct interpreter calls stand in for a phone action anywhere in this path — using the same production agenda deck (`content/decks/trade/agendas.json`) and incident deck (`content/decks/trade/frames.json`) the sim harness and M1 demo both use.

**Known limit of this document:** the author of this walkthrough could not run it end to end in a real browser across real devices (no browser or multi-device network available in that session). Every piece below is unit/integration-tested against injected fakes (a fake trystero room, in-memory transport encryption) — see `packages/ui-shared/src/session/host-session.test.ts`, `packages/ui-phone/src/App.test.tsx`, and `packages/ui-shared/src/SocialApp.test.tsx`. The steps below are the intended walkthrough, written from that tested behavior, not a confirmed pass. The owner's manual run is what actually closes this out (Plan §6.2) — see **Known gaps** and the blank **Run record** below.

## Launch the local demo

The shared screen and each phone are separate apps. Trystero's default signaling strategy needs outbound internet access to reach its public relays for the initial peer handshake (the actual game data, once connected, flows peer-to-peer); a phone on the same WiFi as the shared-screen machine but with no internet route to those relays will not pair.

**Terminal 1 — shared screen:**
```sh
pnpm build:pages
pnpm --filter @telemetry/ui-shared exec vite preview --host 0.0.0.0 --port 4173 --strictPort
```
On the shared-screen machine (or a projector/TV browser), open `http://127.0.0.1:4173/telemetry-engine/social.html`.

**Terminal 2 — phone app (one dev server serves every phone):**
```sh
pnpm --filter @telemetry/ui-phone exec vite --host 0.0.0.0
```
On each phone (or a second/third desktop browser window standing in for one), open `http://<shared-screen machine's LAN IP>:5173/` (the port vite prints).

### Automated simultaneous-pairing preflight

`pnpm test:e2e -- pairing` launches the real shared screen and three real phone tabs, submits all
three manual codes together through Trystero's public signaling relays, and fails if the host does
not reach **Deal agendas** within 30 seconds or any page reports a console/page error. This is a
repeatable BL-11 pairing check, not a substitute for the full walkthrough below.

## Walkthrough

1. On the shared screen, confirm the page title reads **Telemetry Engine — social scene** and a **Pairing** section shows three "Hand the device to <name>" prompts (Zhan, Deuce, Brennan).
2. For each of the three players: on the shared screen, select **I am <name>. Show private pairing card.** Confirm a QR code and a labeled private full-length manual code both render, and that the screen states the code is private to that seat.
3. On each player's phone, open the phone app. Enter the manual code shown on the shared screen into the **pairing code** field (this walkthrough uses the manual-code path throughout, not camera QR scanning — see Known gaps) and select **Pair**. The phones may submit at approximately the same time; do not deliberately stagger them.
4. Confirm the shared screen's Pairing section shrinks by one card as each player claims their seat, and that once all three have claimed, the Pairing section disappears and a **Deal agendas** button appears. Confirm no phone at any point displays another player's pairing code or claim token.
5. Select **Deal agendas**. Confirm the shared screen's public log gains a `campaign.seedCommitted` entry followed by one `secretRoll.committed`/`agenda.dealt`/`objective.assigned` group per player (three groups) — the seed commitment always precedes every draw (INV-8). Confirm the shared screen never states which player received the real agenda versus the routine objective.
6. On each phone that was dealt the deck's real agenda (`content/decks/trade/agendas.json`'s `agenda:independent-skim`, tier orthogonal — this demo's fixed seed, `social-demo-4`, is chosen specifically to deal this agenda to two of the three seats at the deck's own published 0.28 odds), confirm the phone shows a **Comms** heading with a countdown and one enabled action button (`Divert one crate off the manifest.`). On the third (routine) phone, confirm it shows **Private traffic. Nothing to queue this window.** instead — never the action menu.
7. On **both** phones holding the real agenda, select the queue action. This is the "two colliding actions" step: both players are diverting the same loaded crate, and the phase engine's seeded close-order (Spec §3.3) resolves which one actually lands and which one fizzles — confirm each phone's own countdown keeps running and neither phone is told the outcome before the window closes.
8. On the shared screen, select **Close comms window**. Confirm the public log gains the resolved `cargo.diverted` fact (and, if the collision produced one, an `action.fizzled` entry) and then a `lock.cycled` entry — the incident surfacing through the real `generate` step, not a scripted announcement.
9. On any phone, confirm an **Accuse** section now lists the other two players by name. Select one to accuse. Confirm the shared screen's **Confrontation** panel appears, naming the declarer and the accused.
10. On each of the three phones, confirm a **Vote** heading appears asking whether the accused keeps the envelope sealed, and cast a ballot (Yes/No) on each. Confirm the shared screen's confrontation panel updates its per-player Yes/No/Waiting tally live as each vote lands, and that a strict majority carries or fails per Spec §4/§10.2 — a carried vote should show the forced envelope's contents on the shared screen only after the vote actually carries, never before, and never as a voluntary open.
11. Once the vote resolves, select **Verify black box** on the shared screen. Confirm it reports every draw's preimage verifying against its published commitment (no failed draws) — the campaign seed committed before play, re-derivable now that the campaign is over.
12. Confirm the browser console shows no errors on the shared screen or any phone at any point in the walkthrough.

## Pass criteria

- Every clean-checkout command exits successfully.
- Pairing works by manual code on every phone when the three submissions are approximately simultaneous; no phone ever displays another seat's private material.
- Agendas deal at the deck's real, published odds (0.28) — this demo's fixed seed is chosen so two of three seats receive the real agenda, satisfying the "two colliding actions" requirement without lowering the odds setting to force it.
- The comms window accepts two colliding actions and resolves them through the real seeded close-order, not an ad hoc tie-break.
- The incident surfaces through the phase engine's `generate` step (a `lock.cycled` fact and its supporting facts), not a direct ledger write standing in for one.
- The confrontation panel's per-player tally updates after each vote lands, not just once at the end.
- A carried vote opens the envelope only after carrying, never voluntarily; a failed vote never opens anything.
- Black-box verification reports every draw's preimage checking out against its commitment.
- No console error appears on the shared screen or any phone.

## Known gaps (not covered by this walkthrough)

- **Disconnect and hotseat fallback are not implemented in this build.** M2-13's `DisconnectPanel`/hotseat components ship and are unit-tested (`packages/ui-shared/src/shared-screen/DisconnectPanel.test.tsx`, `social-scene.e2e.test.tsx`), but `SocialApp.tsx` doesn't yet wire an operator-driven disconnect control or real WebRTC peer-leave detection into this walkthrough — see `docs/handoffs/M2-15b-2.md` for why (real ICE-timeout-based disconnect detection would make a live demo's "force a disconnect" step hang for 10-30 unpredictable seconds; the intended design is an operator-driven pause control layered on the already-shipped panel, not built by this card). The Plan's exit-demo language names this step; it cannot be walked through yet.
- **No camera QR scanning.** Every phone in this walkthrough pairs by typing the manual code shown on the shared screen. `PairingCard` renders a real QR code too, but nothing in `ui-phone` decodes a camera image — screens-v2 §10's camera-independent path is the only one implemented.
- **Accusation and vote controls are minimal.** The phone's Accuse/Vote UI is functional but not the polished "identical shell regardless of agenda status" component set screens-v2 envisions long-term; this card's own scope cut is that it needs to cover this walkthrough, not the full M2 feature set.
- **Only one incident, one accusation, one vote per run.** The social-scene phase script (`content/frames/social-scene/turn.json`) is a single scene, not a multi-turn campaign; there is no "next incident" or session-continuation path.
- **Sim thresholds:** the sim harness's L2/L3/L5 lineups complete real agenda/comms/confrontation/black-box cycles and hold the structural invariants (INV-5/8/10: no unique twin attribution, every draw verifies), but Spec §21.4's numeric misattribution-rate band (25-40%) is not asserted — it's currently unreachable without content/policy tuning against shipped M2-06 code. Tracked as `docs/tasks/BL-07.md`, owner-descoped from this card on 2026-07-19.
- **`pnpm test:integration` currently fails, independent of M2-15b.** See the clean-checkout section above and `docs/tasks/BL-08.md`.
- **The full walkthrough has not been run.** The narrower automated BL-11 simultaneous-pairing preflight passed on 2026-07-26, but the agenda-through-black-box sequence below remains unverified in a real browser. See the note at the top of this document and the blank Run record below.
