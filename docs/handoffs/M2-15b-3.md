## A real, unresolved test-environment finding, worth reading before touching `SocialApp.test.tsx` again

`SocialApp.test.tsx`'s second test deliberately stops after the deal → comms-window-open transition, not the full accuse/vote/black-box scene. Chasing why cost a large fraction of this session, so the finding is worth recording precisely: driving the fuller scene requires several more fire-and-forget async host updates in tight sequence (comms.queue → close comms window → accuse → three votes → verify). In this jsdom test environment specifically, a render triggered this way was directly observed — via console tracing of both `host.ledger`'s contents and React's own computed render output — to compute with fully correct data, but **never commit to the actual DOM**, reproducibly, even after:
- wrapping the triggering async work in `act()` and awaiting the real underlying promise (not just firing and forgetting),
- adding multiple additional `act()`-wrapped macrotask-tick flushes afterward,
- waiting up to 15 seconds via `waitFor`.

This is not a timing issue (ruled out by the 15s wait) and not a logic bug (the identical `host-session.ts` logic this drives is exhaustively covered, DOM-free, by `host-session.test.ts`'s own full pairing/deal/comms/incident/accuse/vote/black-box scene — that test passes reliably every time, no `act()` gymnastics needed, because nothing there depends on a DOM commit). It looks like a jsdom/React 18 commit-scheduling interaction specific to stacking several fire-and-forget-triggered renders in one jsdom test session, but the exact mechanism was not pinned down. If a future session wants the fuller `SocialApp` scene under test, don't start by re-deriving this — start by either (a) accepting the same trimmed scope and treating `host-session.test.ts` + `ConfrontationPanel.test.tsx` as sufficient coverage of the underlying logic and rendering respectively, or (b) trying a structurally different test approach (e.g., driving the scene through real rendered `ui-phone` `<App/>` instances instead of raw encrypted-message injection, since `ui-phone/App.test.tsx`'s own fire-and-forget pattern *does* work reliably with plain `waitFor` — there may be a structural difference worth isolating between that working case and `SocialApp`'s non-working one, but this session didn't find it despite looking).

`SocialApp.tsx` uses a `useRef`-guarded pattern instead of `useState`'s lazy initializer for constructing its `HostSession`, specifically because this component's render body was observed running more than once for a single mount in this same test harness (not React StrictMode — confirmed off in this repo's testing-library config) — the exact cause wasn't pinned down either, but the `ref.current` guard is robust to it regardless of mechanism, and is cheap enough to keep even if it turns out to be unnecessary in a real browser.
