# M3-11 — Traveller plugin assembly: a real Plugin object

## Objective
`packages/plugin-traveller` stops being `export {}` and becomes a real Spec §15 `Plugin` the app
registers and uses.

## Context
Every M3 packet before this one builds a piece in isolation: hex math, SEC parsing, travel, the
character importer, edges. Nothing assembles them into the `Plugin` object Spec §15 declares
(`id`, `persona`, `dice`, `characterSchema`, `importCharacter`, `careerEdges`, `economy`,
`travel`), and nothing registers that plugin with the running app.

**This card exists because M1 and M2 both learned the same lesson the hard way.** M1-13 and
M2-15 each discovered mid-milestone that no earlier card had actually assembled the shipped
pieces into a runnable whole; the M1 retro turned that into a Plan §5 rule — a task standing up a
whole new package or assembly surface is split out at planning time. `plugin-traveller` is
exactly that surface, so the split is made here, up front, rather than discovered late.

Frontier: public interface assembly plus the INV-1 boundary.

## Amendment (2026-07-26, frontier, at dispatch)
Original owned_paths assumed the engine-side `Plugin` type already existed; it doesn't
anywhere (`plugin-api/index.ts`'s own comment names this card as the one that adds it).
Amended before implementation.

**`plugin-traveller` now depends on `@telemetry/engine`** (`package.json` added to owned
paths above) — a reconsideration of the M3-01/06/07/09 precedent, not a continuation of it.
Those cards avoided the dependency because their own narrow modules (Hex, Ship, CrewMember,
EdgeDef) didn't need engine types; this card's entire job is producing an object the
engine's `Plugin` interface describes, and `@telemetry/plugin-stub` already depends on
`@telemetry/engine` for exactly that reason. The stated objection to a workspace dependency
("moves plugin-traveller in the `tsc --build` graph") does not apply: neither package's
`tsconfig.json` sets `composite`/`references`, so no such graph exists to move it in. `index.ts`
now directly type-annotates its export as `Plugin`, checked at the assembly site itself
rather than only in a separate test. `edges.ts`, `hex.ts`, `travel.ts`, and `character.ts`
are unchanged and keep their own independent no-dependency decisions.

**Corrected acceptance criterion:** "with no sector loaded, the assembled plugin reports
`'unknown'` distance" conflated two different distance concepts that were never unified —
`travel.distance` (hex arithmetic, M3-01/M3-06, real regardless of sector-import state,
needed for jump validation since a crew always knows real parsecs by counting hexes
themselves per rulebook flavor) vs. sector-membership-checked distance (M3-04's
`restoreSector().distance()`, used directly by `resolveInformationHorizon` for market-feed
trust mode — never through `Plugin.travel` at all, confirmed by `tests/integration/
m3-horizon.test.ts` passing a `TravellerSector` directly, not the plugin). Assembly does not
change this: `travel.distance` keeps M3-01's original "`'unknown'` only on unparseable hex"
behavior, tested below; the "no sector loaded" framing is dropped as inaccurate rather than
carried forward as an untestable requirement.

**Second real bug found while wiring:** M3-09's `EdgeProposal.t.slot` was typed as bare
`string`, which does not structurally satisfy the engine's `AppendInput.t.slot: BeatSlot` —
so `useEdge`'s output never actually typechecked into `commitEdgeUsed`, unproven since
neither had a caller. Fixed in `edges.ts` (a local `BeatSlot`-matching string-literal union,
matching M3-01's structural-typing precedent — this one file keeps its no-engine-dependency
decision even though `index.ts` no longer does) and proven with an end-to-end `useEdge` →
`commitEdgeUsed` → ledger test in `tests/integration/m3-plugin-assembly.test.ts` (kept in
`tests/integration/` regardless of the dependency reconsideration above, since it exercises
`edges.ts` + `phases/commits.ts` + the real ledger together — three modules, two of them
still cross-package by relative import).

## Acceptance tests
`packages/plugin-traveller/src/index.test.ts` and `tests/integration/m3-plugin-assembly.test.ts`
— lead-authored at dispatch. Cases:
- the exported `travellerPlugin` satisfies the full §15 `Plugin` interface, checked directly at
  its declaration (`index.ts` type-annotates the export as `Plugin`) and exercised at runtime
- `importCharacter` on a fixture yields the same result as calling M3-07's `importCharacter`
  directly — the assembly adds no behavior of its own (it is the same function reference)
- `travel.distance` on fixture hexes matches M3-01 directly (real parsecs for well-formed hexes,
  `'unknown'` only for an unparseable one); `stalenessWeeks` matches Spec §7.2
- `dice.check` follows the standard 2d6 convention with characteristic DM and skill level, on a
  hand-checked table including a critical success and failure
- a Merchant crew member's `useEdge` proposal commits end-to-end through `commitEdgeUsed` into a
  real ledger (`tests/integration/`, closes the untested M3-09 seam named in the amendment above)
- persona/lexicon strings pass a manual maggie-voice review — **not** `pnpm lint:content`, which
  only schema-validates `content/frames`/`content/decks` and never scans `.ts` source strings
  (same gap already logged on M3-10)
- **INV-1: `pnpm build:stub` passes with `plugin-traveller` deleted** — the IP proof, unchanged
