# BL-04 — `pnpm typecheck` only checks ui-shared and ui-phone, not the other five packages

## Context
Discovered while adding a type-level test to `packages/engine/src/render/renderer.test.ts`
(M1-09): `package.json`'s `typecheck` script has only ever run
`tsc --noEmit -p packages/ui-shared/tsconfig.json && tsc --noEmit -p packages/ui-phone/tsconfig.json`.
Neither ui-shared's nor ui-phone's tsconfig references `packages/engine` via TS project
references, so **no gate has ever type-checked `packages/engine`'s own source or test files** —
every type error in the engine since M0 would have had to be caught by `vitest run`'s esbuild
transform (which does not type-check at all) or a reviewer's eyes, not by `pnpm typecheck`.

`packages/engine`, `packages/plugin-stub`, and `packages/plugin-traveller`
each have a `tsconfig.json` that already `tsc --noEmit`s clean today. `packages/content-lint`
does not: its one test file uses `node:child_process`/`node:url`/`import.meta.url`/`process`
without a Node types setup, which is a real, separate gap (missing `@types/node` or an
equivalent lib/types config) — fixing it needs a new dependency, which is a stop-and-ask
condition per CLAUDE.md, not something to guess at while fixing the typecheck script's coverage.

M1-09's own green commit adds `packages/engine`'s tsconfig to the `typecheck` script (needed to
make that task's own `@ts-expect-error` type-level test meaningful), but stopped there rather
than also sweeping in plugin-stub/plugin-traveller/sim/content-lint, since only `engine` was
required by that task.

**Update (M1-12):** `packages/sim` no longer belongs in the "already clean" list above — its
skeleton (`export {}`) never exercised this. Once M1-12 gave it real modules that (a) use
`node:fs`/`process`/`import.meta.url` (content-lint's exact missing-`@types/node` gap) and (b)
import `packages/engine/src/**` across the package boundary the way content-lint's *tests* do,
`tsc --noEmit -p packages/sim/tsconfig.json` now fails with both the Node-types errors and a
second, distinct class: `TS6059`/`TS6307` ("File X is not under rootDir" / "not listed within the
file list of project Y") on every cross-package import, because neither tsconfig declares a
`references` entry to the other and `rootDir`/`composite` assume a project only contains its own
files. `vitest` doesn't hit this because its on-the-fly esbuild transform never runs a full
project-wide `tsc` type-check — it explains why this shipped fully green through `pnpm test` /
`pnpm lint` / `pnpm typecheck` (the last of which never looked at `packages/sim` either). Fixing
this for real needs either genuine TS project references (`sim`'s tsconfig referencing `engine`'s,
mirroring `build-stub.mjs`'s existing `tsc --build` precedent) or a resolution-mode change; either
is more than a one-line script edit, so it's left for whoever picks up this card rather than
guessed at here.

## Closed 2026-07-25

Fixed without needing TS project references, and without touching `content-lint`. The actual root
cause of `sim`'s `TS6059`/`TS6307` errors wasn't project-reference wiring — it was that `sim`
reached across the package boundary with relative imports (`../../engine/src/generate/frame.js`,
etc.) instead of the package specifier `@telemetry/engine`, the way `plugin-stub` already does
correctly. `packages/engine/src/index.ts`'s barrel already re-exports everything `sim` needed
(`generate`, `degrade`, `oracle`, `npc`, `ledger/types`, `rng`, `time`), so the fix was: declare
`@telemetry/engine` as a real `workspace:*` dependency in `packages/sim/package.json` (it had none
before — a real gap independent of typechecking), rewrite the four import sites in
`campaign.ts`/`lineups.ts`/`social-cycle.ts` to the package specifier, then add `plugin-stub`,
`plugin-traveller`, and `sim` to the `typecheck` script. The Node-types gap this card originally
attributed to `sim` (from the M1-12 update note) did not reproduce — `sim`'s `tsc --noEmit` is
clean with no `@types/node`-related errors, for reasons not fully traced (some pnpm hoisting
detail); not chased further since the outcome is verified clean and stable.

Verified per the card's own method: a deliberate type error introduced in each of
`plugin-stub`/`plugin-traveller`/`sim` was caught by `pnpm typecheck` and reverted.

**`content-lint` decision: excluded, not fixed.** Investigating it surfaced more than the
Node-types gap this card described: `content-lint`'s test files have the *same* relative-import
boundary problem as `sim` had (`TS6059`/`TS6307` reaching into `packages/engine/src` directly) —
fixable the same way — but also several unrelated, genuine type errors in test fixtures
(`TS2532` possibly-undefined array access, `TS2353`/`TS2739` object literals not matching their
declared payload shape, `TS7016` a same-directory JS import missing a declaration). Fixing those
means editing test-fixture code with content-lint domain knowledge this card doesn't carry, which
is scope creep past "wire up the typecheck script." `content-lint` stays outside `pnpm typecheck`
for now; a future card (not filed here) should re-scope it as "fix content-lint's own real type
errors," not just "add its tsconfig to the script."
