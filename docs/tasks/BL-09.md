# BL-09 — `milestone/M2`'s CI gate has been failing since 2026-07-19

## Context
Discovered while verifying `milestone/M2` after merging `main` into it (two-tier method adoption)
and pushing. `gh run list --branch milestone/M2` shows the `gate` job's `pnpm test` step failing
on every push from `feat(m2): add black-box artifact assembly and verification` (2026-07-19T20:18,
last green) onward — the entire second half of the M2-15b session, plus both of this session's
merge/deferral pushes. Nobody caught it because M2 never opened a PR (by design, per the
grandfathered single-PR-at-milestone-end model), so there was no required-check surface forcing
anyone to look at push-triggered CI on `milestone/M2`.

The failure does not reproduce locally (verified on this machine, Node v26):

```
TypeError: Failed to execute 'importKey' on 'SubtleCrypto': 2nd argument is not instance of
ArrayBuffer, Buffer, TypedArray, or DataView.
 ❯ importKey packages/transport/src/index.ts:106:24
 ❯ Module.encryptMessage packages/transport/src/index.ts:114:11
```

**What's been ruled out:** `packages/transport/src/protocol.test.ts` — the actual unit/property
tests for `encryptMessage`/`importKey`/`bufferOf`, run in vitest's default `node` environment —
pass everywhere, including in CI, both before and after this failure appeared. The crypto logic
itself is not implicated.

**What's implicated:** both failing tests (`packages/ui-shared/src/SocialApp.test.tsx`,
`packages/ui-shared/src/shared-screen/social-scene.e2e.test.tsx`) declare
`// @vitest-environment jsdom` and call the real `encryptMessage` to simulate an inbound phone
message from inside a jsdom-rendered React test. jsdom ships its own `crypto`/`SubtleCrypto` shim,
separate from Node's native WebCrypto. The working hypothesis (not yet confirmed by a fix): jsdom's
`crypto.subtle.importKey` is rejecting a real Node-realm `ArrayBuffer` — a cross-realm identity
mismatch, not a logic error — and it evidently only surfaces under whatever jsdom+Node combination
GitHub Actions' now-forced Node 24 runner produces (the workflow requests Node 20;
`actions/setup-node@v4`'s own deprecation warning confirms GitHub is silently substituting Node 24
in every job). `main`'s CI is unaffected only because `main` has no transport-crypto code yet.

**Why this matters and why it isn't a shipped-product bug:** a real browser tab is a single JS
realm — there is no jsdom shim in production, so this specific failure mode cannot occur for an
actual player, and the crypto logic itself is proven correct by `protocol.test.ts`. But it is a
real gate defect: the two tests that fail are exactly the ones proving the *assembled* app's
crypto path works end-to-end (a rendered `SocialApp`/comms scene actually encrypting/decrypting a
real phone message), and they have been silently red in CI for a week on every push with nobody
watching.

## Tests first
- root-cause the exact jsdom/Node mismatch (likely: jsdom's `crypto` shim validates its argument
  against its own realm's `ArrayBuffer` constructor rather than structurally) and add a regression
  test that fails under the old behavior and passes under the fix
- confirm the fix under Node 24 specifically (CI), not just locally under whatever Node version a
  future session happens to run

## Done when
- `pnpm test` passes in CI (`gate` job) on `milestone/M2`, not just locally
- the fix does not weaken `protocol.test.ts`'s existing crypto property/unit coverage
- a short note records which of the two plausible fixes was taken: (a) make `bufferOf`/`importKey`
  robust to cross-realm typed arrays (e.g., construct via whatever `crypto` global the calling
  realm actually provides, or validate structurally instead of relying on `SubtleCrypto`'s own
  instanceof check), or (b) restructure `SocialApp.test.tsx`/`social-scene.e2e.test.tsx` to drive
  the real crypto path through a non-jsdom-realm boundary

## Do not
- do not skip, delete, or weaken `SocialApp.test.tsx` or `social-scene.e2e.test.tsx` to make the
  gate pass
- do not touch `packages/transport/src/protocol.test.ts`'s existing passing coverage
- do not assume this is fixed just because it passes locally — verify against CI (push to
  `milestone/M2` or an equivalent Node-24 environment), since the whole defect is that local and
  CI disagree
