# BL-03 — Type-check the INV-6 ledger-write lint rule instead of name-matching it

## Context
`eslint-rules/no-ledger-writes-outside-interpreter.js` was written in M0-01, before the real
`Ledger` type existed (M0-02). It is a v0 syntactic matcher: it flags `<ident>.append(...)` only
when the identifier is literally named `ledger` and the file isn't under `packages/engine/src/
phases/`. A rename (`const l = getLedger(); l.append(fact)`) or a function parameter
(`function commit(store) { store.append(fact); }`) slips past it undetected — INV-6 (only the
phase-engine interpreter writes to the ledger) is currently enforced by variable-naming
convention, not by anything that actually knows what a `Ledger` is. Flagged in the M0 retro
(`docs/retros/M0.md`, Spec health #7) — the real `Ledger` type has existed since M0-02 and nobody
has revisited the rule since.

## Tests first
- `eslint-rules/__tests__/no-ledger-writes-outside-interpreter.test.js` gains cases where the
  receiver is provably typed `Ledger` under a different variable name (e.g. via a type-checked
  ESLint rule using `@typescript-eslint/utils`'s parser services, or an equivalent typed-AST
  approach) and the call is still flagged outside `phases/`; and a case where a same-named
  variable that is *not* a `Ledger` (e.g. a plain object with an unrelated `.append` method) is
  correctly left alone — the current rule cannot make that distinction and a fix must.

## Done when
- the rule flags a real `Ledger.append` call regardless of the variable's name, and does not flag
  an unrelated `.append` call on a same-named non-`Ledger` variable
- `pnpm lint` still passes across the existing codebase with no changes required outside the rule
  itself and its tests

## Do not
- Do not weaken the existing name-based cases in the current test suite — add to them, don't
  replace coverage
- Do not touch `Visibility` handling
- If a type-checked ESLint rule requires a new dependency (e.g. `@typescript-eslint/utils`,
  `@typescript-eslint/type-utils`) beyond what's already in the workspace, that is a "new
  dependency" stop condition per CLAUDE.md — flag and get sign-off before adding it

## Closed 2026-07-25

Owner sign-off obtained before touching anything (per this card's own stop condition): added
`@typescript-eslint/utils` and `@typescript-eslint/type-utils` at `^8.19.0` (resolved to `8.65.0`,
matching the already-installed `@typescript-eslint/parser`'s resolved `8.63.0` — the exact-pin
`8.19.0` was tried first and rejected on a `typescript` peer-range conflict with the
already-installed TS 5.9.3).

The rule now uses `ESLintUtils.getParserServices` to get the real TypeScript checker, resolves the
`.append(...)` receiver's type, and checks whether it (or any union member) is a `Ledger` symbol
declared in `packages/engine/src/ledger/ledger.ts` — not just named "Ledger" anywhere, to avoid a
different false-positive class. When no parser services are available (a plain `RuleTester` run,
or any future lint invocation without a TS project configured), it falls back to the original v0
identifier-name check rather than silently linting nothing, so the existing untyped test coverage
keeps working unchanged.

Type-aware linting itself is enabled only for `packages/engine/src/**/*.ts` in `eslint.config.js`
(`parserOptions.project` pointing at `packages/engine/tsconfig.json`) — scoped narrowly since
type-aware linting is real overhead and every other rule in this config is purely syntactic.
Measured: `pnpm lint` still completes in ~1.2s.

Verified two ways: (1) the new fixture-based test cases in
`eslint-rules/fixtures/typed-ledger/` — `fake-append.ts` (named `ledger`, unrelated type, must NOT
flag) and `renamed-real-ledger.ts` (named `store`, real `Ledger`, must flag) — both pass under a
type-aware `RuleTester`; (2) a manual probe appending a real-`Ledger`-typed write named `store` to
`packages/engine/src/economy/market.ts` was caught by `pnpm lint` before being reverted.

Landed as two commits (`98fa943` test/red, next commit feat/green) rather than a Haiku packet: the
new-dependency addition is on CLAUDE.md's forbidden-to-workers list regardless of sign-off status,
so this stayed frontier work once the dependency was approved. Full local gate: `pnpm test`
(419/419), `pnpm lint`, `pnpm typecheck`, `pnpm build:stub` all clean.
