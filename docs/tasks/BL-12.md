# BL-12 — `killGroup` resolves before the process group is dead

## Context
Found 2026-07-25 during M3 planning: `scripts/__tests__/process-tree.test.js` failed on roughly
one run in five, while passing on the other four. Investigating it turned up a real defect rather
than a flaky assertion.

`killGroup(child)` (`scripts/lib/process-tree.mjs`) signals the whole process **group**
(`process.kill(-child.pid, ...)`), which is right, but then waits only for the **tracked child**'s
`exit` event before resolving. A grandchild that takes a moment to die is still alive when the
function returns.

That matters because of how its only real caller works: `scripts/pages-smoke.mjs` spawns
`pnpm --filter @telemetry/ui-shared exec vite preview --strictPort`, so **the process holding the
port is vite — a grandchild of the tracked `pnpm`**. `killGroup` runs in a `finally` to release
that port. If it resolves early, a subsequent run can fail with `EADDRINUSE` against
`--strictPort`. The test was asserting the correct contract; the implementation was racy.

A second, related hole: the early `if (hasExited(child)) return;` skips signalling entirely, so if
the tracked child dies on its own while a grandchild survives, the group is never signalled at all.

## Tests first
`scripts/__tests__/process-tree.test.js` already asserted the right thing; it was only
intermittently red. The grandchild fixture now delays exit ~300 ms on SIGTERM — the way vite
actually behaves — which makes the race deterministic: red every run before the fix.

## Done when
- `killGroup` does not resolve until the process group is actually gone (bounded, then escalating
  to SIGKILL), or the timeout expires
- the group is signalled even when the tracked child has already exited
- `pnpm test` passes repeatedly, not on average

## Do not
- "Fix" this by relaxing the test to poll for the grandchild — that hides a real port leak in
  `pages-smoke.mjs` behind a weaker assertion
- Block on a group that is already gone; `process.kill` throws `ESRCH` and that is the success case

## Closed 2026-07-25

`killGroup` now polls the process group with a signal-0 probe and does not resolve until the
group is actually gone (bounded, escalating SIGTERM → SIGKILL), and it signals the group even
when the tracked child has already exited — the orphaned-grandchild case. `ESRCH` is treated as
the success condition throughout.

Verified with the deterministic fixture from the red commit: red every run before, green after.
