# BL-08 — `pnpm test:integration` fails at HEAD and at its own M1-13/M1-14 origin commit

## Context
Discovered while verifying `docs/demos/M2.md`'s clean-checkout command list actually passes.
`tests/integration/trade-campaign.test.tsx` ("M1-13/M1-14 trade-campaign integration") fails its
very first assertion:

```
AssertionError: expected null to be 'step'
 ❯ expectActiveBeat tests/integration/trade-campaign.test.tsx:8:75
```

`expectActiveBeat("DOCKSIDE")` runs immediately after `render(<App />)` and one
`fireEvent.click` ("I am Zhan"), checking `beat-DOCKSIDE`'s `aria-current` attribute is `"step"`.
It reads `null` instead.

**Confirmed not caused by M2-15b's work**: checked out `tests/integration/`,
`packages/ui-shared/src/App.tsx`, and `packages/ui-shared/src/shared-screen/` at commit
`36c3471` (`milestone/M2`'s tip before this session's first commit, itself well after the
M1-13/M1-14 commits `73b031e`/`1f7ce65` that introduced this test) and re-ran
`pnpm test:integration` against that untouched code — same failure, same assertion. This
predates M2-15b entirely; `docs/demos/M1.md`'s own Run record claims this command passed on
2026-07-18, so either the environment (Node/jsdom/vitest patch versions) drifted since then, or
this was already broken and the M1 Run record's "Pass" for `test:integration` was inaccurate at
the time.

Not investigated further: `packages/ui-shared/src/App.tsx`/`shared-screen/PhaseTrack.tsx` were
untouched by M2-15b (a deliberate constraint -- the M1 demo entry point stays as-is per the
owner's confirmed parallel-entry-point call), and root-causing this is a different shape of work
than M2-15b's app-assembly scope. One plausible lead, not confirmed: the test is fully
synchronous (no `waitFor`/`act()` around the initial render or click), and M2-15b's own session
separately hit a class of jsdom/React 18 "render computed but not committed without an
async-aware flush" issue in `SocialApp.test.tsx` (see that file's own comment) that might be the
same underlying mechanism -- but this is a guess, not a diagnosis.

## Tests first
- root-cause why `beat-DOCKSIDE`'s `aria-current` is unset immediately after the initial render
  in this specific test's synchronous style, and fix either the test or the render path
- re-run `pnpm test:integration` clean

## Done when
- `pnpm test:integration` passes again, restoring `docs/demos/M1.md`'s clean-checkout command
  list to a truthful "all commands must pass" state

## Do not
- do not delete or skip this test to make the gate pass
- do not touch `packages/ui-shared/src/App.tsx` or `shared-screen/` beyond what's needed to fix
  this specific defect -- that surface is otherwise frozen per the M2 parallel-entry-point
  decision
