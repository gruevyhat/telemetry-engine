# BL-10 — Phone client never retries phone→host messages; pairing deadlocks on real transport

## Context

Found 2026-07-25 by running the M2 demo walkthrough in a real browser (the first time the
shipped app ever ran against real trystero signaling — every test uses a synchronous,
pre-connected in-memory fake). Symptom: the phone accepts the manual pairing code, shows
"Waiting for the host.", and hangs forever; the shared screen never sees the claim. No console
errors on either side.

## Root cause (fully diagnosed, not speculative)

The failure chain, each link verified independently:

1. `packages/ui-phone/src/App.tsx`'s `pair()` sends `pair.claim` exactly once, synchronously,
   immediately after `createChannel(sessionId)` — milliseconds after trystero's `joinRoom`.
2. Real peer discovery takes time (measured ~500 ms same-machine with both tabs already open;
   seconds is normal), so zero peers are connected at that instant.
3. trystero's `action.send` iterates over currently-connected peers and resolves silently when
   there are none — no queue, no error (`@trystero-p2p/core` `action-wire.mjs`; there is a
   `sendToPending` option the app does not set).
4. `host-session.ts` is purely reactive: it learns a phone exists only from a received
   `pair.claim`. No `onPeerJoin` push, no rebroadcast to unclaimed peers.
5. Neither side retries anything, so the session deadlocks in step 1's silence.

Ruled out by direct test: relay reachability (raw WebSockets to trystero's default nostr relays
open fine from the browser), relay behavior (a Node repro using the library's own
`createEvent`/`subscribe` got the ephemeral signaling event accepted and cross-delivered on 4 of
the 5 relays selected for appId `telemetry-engine`), ICE (bare `RTCPeerConnection` gathers host
and srflx candidates), and peer discovery itself (two clean tabs joining the same room fire
`onPeerJoin` in ~500 ms and can exchange an action message sent from inside the join handler).

## Why the tests missed it

The acceptance/e2e suites inject a fake hub whose `send` is synchronous and whose "peers" are
connected before the first message. The race cannot exist there. This is the concrete instance
of the M2 retro's "never run against real signaling" disclosure.

## The contract already says what to build

`docs/design/screens-v2.md`'s protocol inventory (the "exhaustive M2 protocol inventory" table)
already prescribes the missing behavior — this card is implementation debt against a written
contract, not a design decision:

- `pair.claim`: "retry while offer is valid; otherwise obtain a new private card"
- `comms.queue`: "resend until acknowledged; queued facts survive disconnect"
- `vote.cast`: "resend until `vote.committed`"

## Done when

- The phone retries `pair.claim` until it receives the pairing response (at minimum: resend on
  every `onPeerJoin`, or buffer outbound envelopes in the transport channel until ≥1 peer is
  connected and flush on join; either satisfies the table's "retry while offer is valid").
- `comms.queue` and `vote.cast` follow their table rows' resend semantics, or a recorded owner
  decision narrows this card to pairing only.
- A test exercises the race: a channel whose peer connects *after* the first send must still
  complete pairing. The fake hub gains a "not yet connected" mode so this stays testable without
  real WebRTC.
- The real-browser walkthrough step this card blocks (demo doc steps 1–4) passes on a desktop
  browser: three tabs pair against the shared screen.

## Do not

- Touch `Visibility` handling, schemas, or the phase engine — this is transport/client wiring.
- Add a message type or change the protocol table without going through screens-v2 first.
- Weaken or delete the existing pairing tests; the new race test is additive.

## Closed 2026-07-25

Fixed in two red/green pairs on `main` (`fa6984f`/`ec2bd56`, `d5bbc6c`/`2a23221`):
transport-level buffering (envelopes sent with no eligible peer connected are held and flushed
in order on join) plus app-level claim-until-answered (the phone re-sends `pair.claim` every
second until the first `state.snapshot` arrives — the mesh race means the first peer to connect
can be another phone that absorbs a single flush, and only the app knows the host answered).
Verified in a real browser: three tabs paired against the shared screen over real trystero
signaling, submitted nearly simultaneously, and the shared screen advanced to "Deal agendas".

**Residual — owner accepted the reading, 2026-07-25:** post-connection resend-until-ack for
`comms.queue` and `vote.cast` per screens-v2's table is intentionally not implemented. The
accepted reading: WebRTC data channels are reliable and ordered once connected, and mid-session
loss is M2-13 pause/reconnect territory (reconnect receives the latest snapshot). No follow-up
card. If a future real-device session ever shows a message lost on an established connection,
that observation reopens this, not a rereading of the table.
